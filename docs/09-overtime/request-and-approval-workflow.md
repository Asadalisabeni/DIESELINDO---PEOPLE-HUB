# Phase 9 — Request and approval workflow

The normal workflow is Employee or Supervisor request → Direct Manager approval → HR actual validation → Payroll inclusion. Submission must occur before the planned start, planned start and end must share one local date, an effective employment assignment and work schedule must exist, and one effective rule must cover the derived day type. The service rejects overlapping active requests and planned duration beyond the rule maximum in the same transaction. Confidential text is encrypted and the request fingerprint makes an identical planned interval fail deterministically.

A Supervisor can create only for a current direct report. If that Supervisor is also the direct manager, maker-checker separation prevents self-approval: the resolver seeks an active overtime-specific delegation, then an upper manager, then scoped HR fallback. There is no automatic approval. Manager approval must complete before planned start and may reduce, but never increase, approved minutes. Reject and revision decisions close remaining approval steps and preserve complete Approval action history.

After work finishes, HR approves only when a current complete non-anomalous Attendance record exists. HR approval atomically stores actual comparison, immutable calculation, payable units, allowances, encrypted validation note, and advances the generic instance to Payroll. Failure leaves the request, Approval current step, and calculation count unchanged. Payroll confirms a valid `YYYY-MM` period only when the HR calculation is eligible, then marks the request as downstream `payroll_eligible`. This action does not open a payroll period, create a payroll item, or calculate money. Employee notification is queued after transaction commit at every decision stage.
